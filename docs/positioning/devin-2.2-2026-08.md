# RoboCo vs. Devin 2.2's Agentic Self-Review and Desktop Computer-Use

Cognition shipped Devin 2.2 advertising two headline capabilities: Devin now agentically reviews its own pull-request diff before handing it off, and Devin can drive a full virtual desktop (GUI computer-use), not just a terminal/editor. Both are pitched as reducing human review burden on agent-produced code.

Source: [Cognition — Introducing Devin 2.2](https://cognition.ai/blog/introducing-devin-2-2)

**Response decision:** no product change is warranted, but the framing needs a direct, honest response rather than silence. RoboCo's review chain is structurally NOT self-review — it is independent multi-stage review across three separate roles culminating in a CEO-only gate before anything reaches master, which is a stronger control than an agent reviewing its own diff. On desktop computer-use, RoboCo has no equivalent today: this codebase provisions throwaway per-task Docker sandboxes for backing services (Postgres/Redis), not a GUI-driving desktop. This note states that gap plainly rather than overclaiming parity, and positions the actual differentiator — the governance chain plus isolated per-task sandboxing — instead.

## Verified facts

1. **RoboCo's PR review is not self-review — it's a dedicated third-party role.** A separate `pr_reviewer` role, never the task's own developer, reviews the assembled PR: `PRGateMixin.pr_pass` / `PRGateMixin.pr_fail` (`roboco/services/gateway/choreographer/pr_gate.py:157-163` and `:195-206`) transition `awaiting_pr_review -> awaiting_pm_review` or `-> needs_revision`. The lifecycle spec restricts both verbs to `frozenset({Role.PR_REVIEWER})` with `self_review_block=True` (`roboco/foundation/policy/lifecycle.py:597-616`), so the same agent that wrote the code is structurally barred from passing its own PR — the opposite of Devin's self-review model.
2. **That PR-review gate sits on top of an independent QA pass.** Before a task's PR ever reaches the `pr_reviewer`, it must clear a separate `awaiting_qa` stage restricted to `Role.QA` (`roboco/foundation/policy/lifecycle.py:240`, `:539-558`) — a second independent agent, distinct from both the developer and the PR reviewer, verifying the work against its acceptance criteria.
3. **Both of those sit beneath a hard, human-only CEO-approval gate before master.** `AWAITING_CEO_APPROVAL -> COMPLETED` (`ceo_approve`) and `AWAITING_CEO_APPROVAL -> NEEDS_REVISION` (`ceo_reject`) are each `allowed_roles=frozenset({Role.CEO})` in the `ActionSpec` table (`roboco/foundation/policy/lifecycle.py:666-684`) — no agent role, including PM roles, can execute either transition.
4. **The CEO-only rule is enforced at the API layer too, not just the state machine.** `require_ceo_role()` (`roboco/api/deps.py:627-640`) raises HTTP 403 unless the caller's role resolves to `Role.CEO`, and is the single shared check the orchestrator router and release-handler gates both delegate to — so a human sign-off is required by two independent enforcement layers (lifecycle spec + API dependency), not one.
5. **RoboCo has no desktop/GUI computer-use equivalent — stated honestly, not glossed over.** A repo-wide search for computer-use / virtual-desktop capability (`computer_use`, `xdotool`, `vnc`, `remote desktop`) returns zero matches in `roboco/`. The closest capability is `PlaywrightMCP`, gated to three cases only: `fe-qa`/`ux-qa` roles, the Product Owner's task-scoped Dogfood spawn, and a `ux_ui` developer spawned onto a `source=video` task (`_is_video_authoring_spawn`, `roboco/runtime/orchestrator.py:3902-3910`) so the author can preview the composition in a real browser while iterating — the actual gate is `roboco/runtime/orchestrator.py:4203-4211` (`playwright_mcp_teams = ("frontend", "ux_ui")`; `browser_qa = (agent_role == "qa" and get_agent_team(agent_id) in playwright_mcp_teams)`; `if browser_qa or video_authoring or dogfood_walk: mcp_servers["playwright"] = {...}`). All three are structured browser tools (navigate/snapshot/evaluate/screenshot), not a general GUI-driving desktop session. RoboCo does not claim parity with Devin's desktop computer-use here.
6. **What RoboCo does provision instead is throwaway, isolated per-task backing-service sandboxes.** `SandboxProvisioner.provision` (`roboco/runtime/sandbox.py:131-180`) spins up sibling Docker containers per agent for opted-in services (Postgres/Redis today, extensible via the `SANDBOX_ENGINES` registry); the hardening specifics — random creds, tmpfs data dir, memory/CPU caps — are in `_provision_engine` (`roboco/runtime/sandbox.py:186`: `password = secrets.token_hex(16)`; `:203-205`: `for mount in engine.tmpfs: args += ["--tmpfs", mount]` then `args += ["--memory", "512m", "--cpus", "1"]`) — and `SandboxProvisioner.teardown` (`roboco/runtime/sandbox.py:306-309`) removes them idempotently at end of engagement. This is a database/cache sandbox for safe dev testing, not a GUI desktop, and this doc does not represent it as one.

RoboCo's differentiated posture: where Devin collapses review into the same agent that wrote the code, RoboCo enforces independent review at three separate, role-checked layers — a distinct `pr_reviewer`, a distinct QA pass, and a human-only CEO gate that the API itself refuses to bypass — a stronger governance chain than agentic self-review. On desktop computer-use, RoboCo concedes the gap honestly rather than claiming false parity, and offers isolated per-task backing-service sandboxing as the adjacent, verifiably real capability instead.
