# AI-Generated Code Risk Figures (Sonar 42%, AppSec Santa 25%) vs. the Gates Between RoboCo Agent Output and Master

Thoughtworks' Agent/works launch release (June 16, 2026) frames AI-generated code as a risk that needs governance, and backs the framing with two third-party figures. Buyers who read the second figure may assume it describes RoboCo's output too. This note records what the two figures say, why they are not a measurement of RoboCo, and which gates, each verified directly in this codebase, stand between an agent's output and master.

Source: [Thoughtworks Launches Agent/works to Govern and Run Enterprise AI Agents Across Any Cloud](https://www.thoughtworks.com/about-us/news/2026/thoughtworks-launches-agent-works)

## The two figures, verbatim

The release states: "According to Sonar's 2026 State of Code Developer Survey, developers report that 42% of committed code is now AI-generated or AI-assisted. At the same time, research from AppSec Santa found that 25% of AI-generated code samples contained critical security vulnerabilities."

These are industry-wide figures from other parties' surveys and samples. The first is self-reported developer survey data about how much committed code is AI-assisted. The second describes a research sample of AI-generated code. Neither was collected on RoboCo output, and this note does not reinterpret them.

**Response decision:** no product change is warranted. The honest answer to "does the 25% apply to you" is not a competing number. It is a description of what a change has to pass before it can reach master. Each gate below is cited to the file that implements it.

## Verified facts: the gates between agent output and master

1. **Agent output is never reviewed by its own author.** Role separation is enforced in the lifecycle spec, not by convention. `qa_pass` and `qa_fail` are restricted to `_QA_ROLES` and carry `self_review_block=True` (the `qa_pass` and `qa_fail` entries in `ACTIONS`, `roboco/foundation/policy/lifecycle.py`, `AWAITING_QA -> AWAITING_DOCUMENTATION` / `-> NEEDS_REVISION`). A developer submits through `i_am_done`; the QA role is a different agent.
2. **QA passes need per-criterion evidence.** `pass_review` validates a `criteria_verified` argument (`_validate_criteria_verified`, `roboco/services/gateway/choreographer/qa.py`), one evidence entry per acceptance criterion with a length cap on each entry, so a bare "looks good" pass is rejected. This is a statement about the review protocol, not about defect rates.
3. **An independent PR-reviewer gate checks the assembled PR before the PM merge.** `pr_pass` and `pr_fail` are restricted to `_DEVOPS_ROLES`, which is `{Role.PR_REVIEWER, Role.DEVOPS}`, and both carry `self_review_block=True` (the `pr_pass` and `pr_fail` entries in `ACTIONS`, `roboco/foundation/policy/lifecycle.py`, `AWAITING_PR_REVIEW -> AWAITING_PM_REVIEW` / `-> NEEDS_REVISION`). The PR reviewer is the standing reviewer; the DevOps role takes part only when the DevOps floater is armed (`ROBOCO_DEVOPS_ENABLED`), where it co-reviews PRs that touch the project's declared infra files. The verbs live in `roboco/services/gateway/choreographer/pr_gate.py` (`pr_pass`, `pr_fail`).
4. **`pr_pass` refuses on its own checks, not just reviewer opinion.** The pass path lives in `roboco/services/gateway/choreographer/pr_gate_pass.py` and runs, in order, a toolchain guard (`_toolchain_broken_guard`), a conventions guard (`_conventions_guard`) and a CI-status guard (`_ci_status_guard`). The CI guard blocks the pass while the assembled PR's head-commit checks are failing, pending, unscheduled or unresolvable. `pr_fail` stays available regardless. Two accurate caveats: a project with no CI configured passes through with an evidence note rather than blocking, and a failing CodeQL check whose analyzed language falls outside the task's declared `intends_to_touch` scope is not counted against the task (`_scope_gate_codeql_failure`), because CodeQL scans a whole language rather than the diff. The repo ships CodeQL workflows (`.github/workflows/code-ql.yml`, `.github/workflows/codeql-js-ts.yml`).
5. **Only the CEO can complete a task awaiting CEO approval.** `ceo_approve` is restricted to `frozenset({Role.CEO})` (the `ceo_approve` entry in `ACTIONS` and its `StatusTransition`, `roboco/foundation/policy/lifecycle.py`, `AWAITING_CEO_APPROVAL -> COMPLETED`). The HTTP route `POST /api/tasks/{id}/ceo-approve` (`ceo_approve_task` in `roboco/api/routes/tasks.py`) checks `agent.role != AgentRole.CEO` inline and returns 403 otherwise, and rejects an approval whose notes are shorter than the minimum, so every approval leaves a written rationale. The shared helper `require_ceo_role()` (`roboco/api/deps.py`) is the single CEO check that other CEO-only routes call (for example `roboco/api/routes/dashboard.py` and `roboco/api/routes/entire.py`); the approve route itself does not call it. The company charter also lists "CEO approves every merge to master" as a standing constraint.
6. **The architectural conventions validator is a deterministic placement check, and it is opt-in.** `.roboco/conventions.yml` declares which kinds of definition may live in which module (for example, no data model in `roboco/api/routes`, no route in `roboco/services`) and the validator refuses forbidden placements. It is wired into two gates: `i_am_done` (`_conventions_gate`, `roboco/services/gateway/choreographer/_impl.py`) and `pr_pass` (the conventions guard above). It is **default-off**: `conventions_enabled` defaults to `False` (`Settings.conventions_enabled`, `roboco/config.py`) and every enforcement hook is inert when off. Where it is on, only block-level findings refuse a submit.
7. **Lint and type suppressions are a block-level rule.** `no_lint_suppressions` is not overridden to `warn` in `.roboco/conventions.yml`; the file's closing comment on defaults states that everything not listed inherits the derived block level, naming `no_lint_suppressions` (block since 2026-10). The sweep left one suppression, a `# nosec B108` in `roboco/llm/providers/nebius_sandboxes.py`, and it carries a written waiver in the `waivers:` section of the same file. A new inline `noqa` / `type: ignore` / `nosec` therefore fails the validator wherever the standard is armed. As with gate 6, this applies only when `conventions_enabled` is on.
8. **`make quality` is the full merge gate and runs bandit inline.** The `quality` target in the `Makefile` runs, in order: compose-sync, `ruff format --check`, `ruff check`, the markdown prose check, the codebase-map verify (`scripts/verify_codebase_map.py`), the map-concatenation check (`scripts/rebuild_map_concat.py --check`), `mypy`, `pytest` with `--cov-fail-under=75`, `xenon`, `radon mi`, `vulture`, then `uv run bandit -r roboco/ -ll`, `pip-audit`, `deptry`, an Alembic SQL parse, `import-linter` and the foundation drift checks. The bandit call is its own step inside `quality`'s recipe. It is not a dependency on the standalone `bandit` or `security` targets, and the `-ll` flag limits reporting to medium severity and above. Bandit's configuration is in `pyproject.toml` (`[tool.bandit]`, which excludes `tests`, `.venv`, `vulture_whitelist.py` and `alembic`, and sets `severity = "medium"`). CI runs `make quality` (the "Run quality gate" step in `.github/workflows/ci.yml`).
9. **`make gate` does not run bandit.** The `gate` target (`Makefile`) is the fast pre-submit gate: `ruff format --check`, `ruff check`, `mypy`, `xenon` and `lint-imports`, with no tests and no bandit. A project's pre-submit command is configurable (`roboco/models/project.py` describes it as lint, types and complexity with no tests, "e.g. 'make gate'"), and `i_am_done` runs it in the developer's workspace. The standalone `make bandit` target and `make security` (which lists the `bandit` and `pip-audit` targets as prerequisites) exist for running the scan on its own. Static security scanning therefore happens in the full gate (`make quality`, which CI runs) and not in the fast pre-submit gate.

## How the gates sequence

A leaf task goes developer, then QA, then documenter, then PM-assembled PRs. Each assembled cell-to-root and root-to-master PR passes the PR-reviewer gate before the PM merges. A task escalated for sign-off lands in `awaiting_ceo_approval`, where only the CEO can complete it. Leaf developer tasks skip the PR-reviewer gate; the assembled PR is the unit that gate reviews.

## Does not claim

- It does not claim RoboCo-authored code has any particular vulnerability rate, including a rate below the AppSec Santa 25%. No such measurement is made or cited here.
- It does not claim the 42% or 25% figures were measured on RoboCo output, or that they are wrong. They are quoted as third-party findings.
- It does not claim the gates guarantee the absence of vulnerabilities. Bandit at `-ll` reports medium severity and above, CodeQL is scoped by language, and review is a process, not a proof.
- It does not claim `make gate` runs bandit. It does not.
- It does not claim the conventions validator is on by default. It is off unless `conventions_enabled` is set, and the `no_lint_suppressions` block applies only where it is armed; one suppression is waived.
- It does not claim `require_ceo_role` is what the CEO-approve route calls. That route checks the role inline; the helper serves other CEO-only routes.
- It does not claim the CI guard blocks `pr_pass` for every project. A project with no CI configured passes through with a note.
- It does not claim any escaped-defect, review-rejection or coverage outcome. Coverage has a gate floor of 75% in `make quality`; this note states the floor, not an achieved figure.
