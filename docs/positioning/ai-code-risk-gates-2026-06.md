# AI-Generated Code Risk Figures (Sonar 42%, AppSec Santa 25%) vs. the Gates Between RoboCo Agent Output and Master

Thoughtworks' Agent/works launch release (June 16, 2026) frames AI-generated code as a risk that needs governance, and backs the framing with two third-party figures. Buyers who read the second figure may assume it describes RoboCo's output too. This note records what the two figures say, why they are not a measurement of RoboCo, and which gates, each verified directly in this codebase, stand between an agent's output and master.

Source: [Thoughtworks Launches Agent/works to Govern and Run Enterprise AI Agents Across Any Cloud](https://www.thoughtworks.com/about-us/news/2026/thoughtworks-launches-agent-works)

## The two figures, verbatim

The release states: "According to Sonar's 2026 State of Code Developer Survey, developers report that 42% of committed code is now AI-generated or AI-assisted. At the same time, research from AppSec Santa found that 25% of AI-generated code samples contained critical security vulnerabilities."

These are industry-wide figures from other parties' surveys and samples. The first is self-reported developer survey data about how much committed code is AI-assisted. The second describes a research sample of AI-generated code. Neither was collected on RoboCo output, and this note does not reinterpret them.

**Response decision:** no product change is warranted. The honest answer to "does the 25% apply to you" is not a competing number. It is a description of what a change has to pass before it can reach master. Each gate below is cited to the file that implements it.

## Verified facts: the gates between agent output and master

1. **Agent output is never reviewed by its own author.** Role separation is enforced in the lifecycle spec, not by convention. `qa_pass` and `qa_fail` are restricted to `_QA_ROLES` and carry `self_review_block=True` (`roboco/foundation/policy/lifecycle.py:546-565`, `AWAITING_QA -> AWAITING_DOCUMENTATION` / `-> NEEDS_REVISION`). A developer submits through `i_am_done`; the QA role is a different agent.
2. **QA passes need per-criterion evidence.** `pass_review` validates a `criteria_verified` argument (`_validate_criteria_verified`, `roboco/services/gateway/choreographer/qa.py`), one evidence entry per acceptance criterion with a length cap on each entry, so a bare "looks good" pass is rejected. This is a statement about the review protocol, not about defect rates.
3. **An independent PR-reviewer gate checks the assembled PR before the PM merge.** `pr_pass` and `pr_fail` are restricted to `Role.PR_REVIEWER` with `self_review_block=True` (`roboco/foundation/policy/lifecycle.py:598-617`, `AWAITING_PR_REVIEW -> AWAITING_PM_REVIEW` / `-> NEEDS_REVISION`). The verbs live in `roboco/services/gateway/choreographer/pr_gate.py` (`pr_pass` at line 215, `pr_fail` at line 253).
4. **`pr_pass` refuses on its own checks, not just reviewer opinion.** In `pr_gate.py` the pass path runs, in order, a toolchain guard, a conventions guard and a CI-status guard (`_conventions_guard`, `_ci_status_guard`, around lines 755-925). The CI guard blocks the pass while the assembled PR's head-commit checks are failing, pending, unscheduled or unresolvable. `pr_fail` stays available regardless. Two accurate caveats: a project with no CI configured passes through with an evidence note rather than blocking, and a failing CodeQL check whose analyzed language falls outside the task's declared `intends_to_touch` scope is not counted against the task (`_scope_gate_codeql_failure`), because CodeQL scans a whole language rather than the diff. The repo ships CodeQL workflows (`.github/workflows/code-ql.yml`, `.github/workflows/codeql-js-ts.yml`).
5. **Only the CEO can complete a task awaiting CEO approval.** `ceo_approve` is restricted to `frozenset({Role.CEO})` (`roboco/foundation/policy/lifecycle.py:667-676`, `AWAITING_CEO_APPROVAL -> COMPLETED`). The HTTP route `POST /api/tasks/{id}/ceo-approve` (`roboco/api/routes/tasks.py:1778`) checks `agent.role != AgentRole.CEO` inline and returns 403 otherwise, and rejects an approval whose notes are shorter than the minimum, so every approval leaves a written rationale. The shared helper `require_ceo_role()` (`roboco/api/deps.py:627-639`) is the single CEO check that other CEO-only routes call (for example `roboco/api/routes/maintenance_pause.py:36`); the approve route itself does not call it. The company charter also lists "CEO approves every merge to master" as a standing constraint.
6. **The architectural conventions validator is a deterministic placement check, and it is opt-in.** `.roboco/conventions.yml` declares which kinds of definition may live in which module (for example, no data model in `roboco/api/routes`, no route in `roboco/services`) and the validator refuses forbidden placements. It is wired into two gates: `i_am_done` (`_conventions_gate`, `roboco/services/gateway/choreographer/_impl.py:2565`) and `pr_pass` (the conventions guard above). It is **default-off**: `conventions_enabled` defaults to `False` (`roboco/config.py:434-435`) and every hook is inert when off. Where it is on, only block-level findings refuse a submit.
7. **Lint suppressions are a warning today, not a block.** The `no_lint_suppressions` rule is declared at `level: warn` in `.roboco/conventions.yml` (line 107), with a comment explaining that roughly 90 unwaived `noqa` / `type: ignore` markers remain under `tests/`. The `roboco/` and `panel/` trees were cleaned in a 2026-07 audit, and the two unavoidable ones carry waivers in the same file. Do not describe this rule as blocking.
8. **`make quality` is the full merge gate and runs bandit inline.** `make quality` (`Makefile:286`) runs, in order: compose-sync, `ruff format --check`, `ruff check`, the markdown prose check, `mypy`, `pytest` with `--cov-fail-under=80`, `xenon`, `radon mi`, `vulture`, then `uv run bandit -r roboco/ -ll` (`Makefile:305-306`), `pip-audit`, `deptry`, an Alembic SQL parse, `import-linter` and the foundation drift checks. The bandit call is its own step inside `quality`'s recipe. It is not a dependency on the standalone `bandit` or `security` targets, and the `-ll` flag limits reporting to medium severity and above. Bandit's configuration is in `pyproject.toml` (`[tool.bandit]`, which excludes `tests`, `.venv`, `vulture_whitelist.py` and `alembic`, and sets `severity = "medium"`). CI runs `make quality` (`.github/workflows/ci.yml:197`).
9. **`make gate` does not run bandit.** `make gate` (`Makefile:345-351`) is the fast pre-submit gate: `ruff format --check`, `ruff check`, `mypy`, `xenon` and `lint-imports`, with no tests and no bandit. It is the command the pre-submit check at `i_am_done` runs in the developer's workspace. The standalone `make bandit` target (`Makefile:221-226`) and `make security` (`Makefile:269`, which is `bandit` plus `pip-audit`) exist for running the scan on its own. Static security scanning therefore happens in the full gate (`make quality`, which CI runs) and not in the fast pre-submit gate.

## How the gates sequence

A leaf task goes developer, then QA, then documenter, then PM-assembled PRs. Each assembled cell-to-root and root-to-master PR passes the PR-reviewer gate before the PM merges. A task escalated for sign-off lands in `awaiting_ceo_approval`, where only the CEO can complete it. Leaf developer tasks skip the PR-reviewer gate; the assembled PR is the unit that gate reviews.

## Does not claim

- It does not claim RoboCo-authored code has any particular vulnerability rate, including a rate below the AppSec Santa 25%. No such measurement is made or cited here.
- It does not claim the 42% or 25% figures were measured on RoboCo output, or that they are wrong. They are quoted as third-party findings.
- It does not claim the gates guarantee the absence of vulnerabilities. Bandit at `-ll` reports medium severity and above, CodeQL is scoped by language, and review is a process, not a proof.
- It does not claim `make gate` runs bandit. It does not.
- It does not claim the conventions validator is on by default, or that `no_lint_suppressions` blocks. It is off by default, and that rule is `warn`.
- It does not claim `require_ceo_role` is what the CEO-approve route calls. That route checks the role inline; the helper serves other CEO-only routes.
- It does not claim the CI guard blocks `pr_pass` for every project. A project with no CI configured passes through with a note.
- It does not claim any escaped-defect, review-rejection or coverage outcome. Coverage has a gate floor of 80% in `make quality`; this note states the floor, not an achieved figure.
