# Workspaces, work sessions, forge providers, protected branches

Migrated from the root CLAUDE.md so it loads only when the matching files are touched.

On a Python workspace, `WorkspaceService` runs `uv sync --extra dev` (not plain `uv sync`) so the clone's `.venv` carries the full gate toolchain (ruff/mypy/xenon/pytest) - the lint/type/complexity tools live in the `dev` **extra**, which plain `uv sync` skips. Without it an agent's `make quality` fails on `ruff: command not found` and the agent can't gate its own work.

Because the clone is shared across a dev's tasks, a **fresh claim** git-resets the workspace to a clean tree (`git reset --hard`) before checking out the new task's branch - discarding abandoned uncommitted cruft from a finished task while preserving all commits and the gitignored `.venv`. A resume short-circuits before this, so committed work is never reset.

Terminal completion and cancellation also force-delete the task's local branch ref and its `.previews/` video-render dir in the assignee's clone (alongside the existing worktree removal), skipping any branch that coincides with an environment-ladder rung; a PM/CEO can additionally sweep older backlog branches project-wide via `POST /git/branches/cleanup` or the Git page's "Clean Up Stale Branches" button.

A task has at most **one active WorkSession**: re-claiming a task (pool release, reaper unclaim, escalation redirect) supersedes any prior agent's stale active session, enforced both at the service layer and by a DB partial-unique index (migration 047). Without it, duplicate active sessions made the one-row active lookup raise and crashed the claim/plan flow into a respawn loop.

A developer's clone is shared across all their tasks, so push and PR-head operate on the task's **recorded branch by name**, independent of the clone's current checkout - fixing the `BRANCH_MISMATCH` / "No commits between" failures when the clone was parked on a later task's branch. A missing local task-branch ref is first recovered from `origin/<branch>` before the push-by-name.

**Stale-state family fixes (2026-07-24, #683/#690/#692).** Three independent chokepoints used to trust whatever a clone/worktree happened to have on disk instead of checking origin, all closed the same week off one live incident: `GitService.rebase_onto_base` no longer opens with an unconditional `reset --hard origin/<head_branch>` (#683) - it classifies local vs origin post-fetch first, so a committed-but-unpushed dev tip (routine mid-rework, since `commit` never pushes) is never silently discarded, and a genuine two-sided divergence returns `{"status": "diverged", ...}` untouched rather than guessing a side to keep. The reader-side twin, `GitService._resolve_head_ref` (backing `diff`/`list_changed_files`/`read_file_at_branch`/`roboco_git_log`), now prefers `origin/<branch>` over a local ref whenever origin carries commits the local ref lacks (#690) - a QA/PM/reviewer clone parked on pre-rebase history no longer stays frozen there across every later review round. And `WorkspaceService.ensure_worktree_self_heal` stops treating an ALREADY-PRESENT per-task worktree as a pure venv+chown no-op (#692): every spawn now runs it through `_refresh_present_worktree`, role-aware via `can_author` (`foundation.identity.WORKTREE_AUTHOR_ROLES`) - fast-forward when behind for every role without ever discarding an author's dirty uncommitted edits, leave alone when strictly ahead, hard-reset only for a non-author reader when diverged. Together these close the "reviewer keeps bouncing a task back for fixes that already landed, because it's still looking at its own frozen round-1 checkout" incident class.

### Who runs what in a workspace (the trust boundary)

Every agent container mounts ALL of `/data/workspaces` read-write, so an agent (possibly prompt-injected by an external PR) controls every byte of every clone at any moment: `.git/config`, `.git/hooks`, attributes, the working tree. The rule is **root never reads, writes, or runs anything under `/data/workspaces`** (exceptions, all by descriptor with `O_NOFOLLOW`, so a symlink an agent plants anywhere on the path is refused, never followed: Docker bind mounts; `remove_workspace_tree`, since a bare `shutil.rmtree` is link-safe inside the tree but resolves the path's ancestors; `prepare_clone_parent`, which creates `<slug>/<team>/` and gives it group `agent_gid` so the git user can clone into a host-made 755 skeleton; and the permission repair below). Known follow-up: the video-preview paths (`<slug>/.previews/`, `task.py` cleanup and `content_actions` frame extraction) still delete, create and extract there as root.

- **Workspace git** goes through `roboco/services/workspace_git.py` only: it runs as `roboco-git` (uid `settings.git_user_uid`, 1500; primary gid `agent_gid`, 1000; no other groups, no capabilities, `no_new_privs`), never root and never the agent uid (on the NAS that is the host user who owns the provider credentials mounted into the orchestrator). Environment from scratch; `-c` overrides pin every program-starting setting (hooks only from the root-owned `/opt/roboco/git/hooks`, no fsmonitor/ssh/askpass/editor/pager/signing, no network protocol except local `file`); `--no-ext-diff --no-textconv` on diff/log/show; `GIT_NO_REPLACE_OBJECTS`. The repository is pinned by layout (`GIT_DIR` / `GIT_COMMON_DIR` / `GIT_WORK_TREE` from `workspace_repository_env`), never discovered: left to discovery, git follows a worktree's agent-writable `.git` gitfile, any git dir's `commondir` file (which moves config, objects and attributes to an agent-chosen directory, past the audit, with no race), or a `.git` planted above the clone. The relay's `upload-pack` gets the worktree admin dir plus `GIT_COMMON_DIR` the same way. A config key no override can pin (filter/diff/merge drivers, `url.*`, `include*`, `core.worktree`, alternates, a non-directory `.git`) refuses the command (`UnsafeWorkspaceGitConfigError`). The audit can lose a race to an agent rewriting the file; the privilege drop is the boundary. Husky's `core.hooksPath=.husky/_` (set by real clones' `prepare` scripts) is neutralized, not refused.
- **Origin traffic** goes through the project's **relay** (`roboco/services/git_relay.py`): a bare repo per project at `<private_data_root>/relays/<slug>.git`, root-owned, mounted into no agent. `GitService._run_git` serves every command that names `origin` (fetch / push / ls-remote / pull --ff-only / remote prune) through it (`roboco/services/git_origin.py`), against the project's URL from the database; anything else is refused, never guessed. The token exists only in root git inside the relay, as `GIT_CONFIG_*` env scoped to the origin host (never argv, never a file); a push takes the commit out of the clone with `upload-pack` running as the git user, and the relay fsck's every object it receives that way (`fetch.fsckObjects`; a crafted `.gitmodules` or tree is refused before it reaches root's repositories — origin fetches are not fsck'd, legacy histories would fail). curl already drops a custom `Authorization` header on a cross-host redirect; the host scoping is defense in depth.
- **REST calls** (PR create/merge/close/...) resolve the repo from the project's `git_url`, never from the clone's agent-writable `remote.origin.url` (`GitService._repo_ref_for_workspace`).
- **Dispatcher-owned repos** live under `/data/private` (orchestrator-only mount): the relays, the conventions/release-readiness read clone (`read/<slug>`), the release clone (`release/<slug>`), and scratch (`scratch/<slug>/...`). Root runs git there via `run_private_git` (no token, no hooks, local transport only); the read and release clones check out with `core.symlinks=false` because root reads and rewrites their files. Their pre-move copies under the workspaces root (`<slug>/_meta/conventions`, `_release/<slug>`) are deleted once by the dispatcher's startup (`remove_pre_move_copies`: only that exact layout of real directories holding a `.git`, symlink-safe; a `pre-move-copies-removed` marker in the private root stops it touching anything created there later).
- **A clone's own code** (the quality gate, codegen, dep installs, the toolchain smoke, the dep-update probe) runs in a throwaway container (`roboco/services/workspace_container.py`): the orchestrator's own image, as the agent uid, `--cap-drop ALL`, `no-new-privileges`, only that clone mounted, no Docker socket, plain `bridge` network, an in-container `timeout`. It never falls back to running here. Before running anything the container compares its mount's device/inode with the identity the orchestrator took through an `O_NOFOLLOW` descriptor walk (dockerd resolves the bind source on the host and would follow a planted symlink); a mismatch exits 125 ("could not start").
- **A project's own hooks** (husky's `.husky/_` shims, a `.githooks` dir, `.git/hooks`) never run in the orchestrator, but the gating ones still gate RoboCo's commits and pushes: `GitService._run_git` runs `pre-commit`, then `commit-msg` (on `<git dir>/COMMIT_EDITMSG`, which it may edit; the commit then reads it back with `-F`), before a workspace `commit`, and `pre-push` (args `origin <db url>`, git's one-line stdin) before a workspace push, each in the throwaway container (`roboco/services/project_hooks.py`). The hook is located by git itself (`workspace_hook_path`: `rev-parse --git-path hooks/<name>` as the git user, honoring the repo's `core.hooksPath`), so husky shims that are not checked out in a per-task worktree are skipped exactly as plain git would skip them. A non-zero exit, a timeout (commit hooks: the commit's own budget, 180 s; `pre-push`: `project_hook_push_timeout_seconds`, 240 s, which must fit with the quality gate inside `i_am_done`'s 900 s wall) or a container that cannot start refuses the command with the hook's output; `--no-verify` skips them; a hook outside the workspaces root (operator `workspace_path`) is skipped and logged. Other hook types are not run. A wrapper Entire installed (`# Entire CLI hooks` near the top) stands for the hook it moved aside, `<hook>.pre-entire`, or for none. git LFS (`filter.lfs.*`) is refused by the audit; `git-lfs` was never installed in the orchestrator image.
- **Entire** (`entire_enabled`, `roboco/services/entire_hooks.py`): agents run Entire's session hooks in their own containers; RoboCo runs its commit hooks for their commits, because the commit runs here. They read the agent-written session record (`.git/entire-sessions/*.json`), which names the transcript file to read, and that file's content lands in a checkpoint that gets pushed (lab-verified: a record pointed at another file put that file in the checkpoint). So `prepare-commit-msg` + `commit-msg` (before the commit, on `COMMIT_EDITMSG`) and `post-commit` (after it) run in the throwaway container with **no network** (`run_offline_in_workspace_container`) and only the clone plus that agent's own transcript folder mounted read-only at the path its session names (`/home/agent/.claude/projects/<cwd with every non-[A-Za-z0-9] as ->`, from `host_claude_dir`, identity-checked like the clone). Without that folder a mid-turn commit gets a trailer but no checkpoint. Entire writes its git objects 0600; the same container gives the agent group read on them, or the git user's `upload-pack` cannot hand the checkpoint to the relay. A push then sends, through the relay, the checkpoint refs (`refs/entire/checkpoints/<id[-2:]>/<id>`, never forced, nothing else accepted by `push_checkpoint_refs`) named by the `Entire-Checkpoint` trailers of the commits it pushes (those on no `origin/*` ref). Best-effort throughout: a failure is logged and never refuses the commit or push. Costs about two container starts per agent commit, only for a clone with a recorded session. Not run: Entire's `pre-push` (needs network and a token) and `post-rewrite` (a dispatcher rebase does not remap the session's linkage; trailers already made survive). The CLI sits in the orchestrator image off PATH (`/usr/local/lib/entire/entire`, same pin as `agent-base.Dockerfile`, a test keeps them equal): on PATH, the `.git/hooks` wrappers would start it from any project hook.
- **Permissions**: the git user and the agent share gid 1000 and both write with umask 002 (agent images run their entrypoints through `umask 002`), so neither needs a chown. Before a clone's first git command or file write (`write_workspace_file`) in a process, and on a "Permission denied" failure, root (the drop required) runs an fd-safe group-write repair (`fwalk` + `O_NOFOLLOW` + `fchown`/`fchmod` of the group only; skips `node_modules`/`.venv`/...). There is no chown walk and no owned-marker any more. Clones made before the git user existed carry the host's group (`admin`, gid 10, on the NAS); the repair moves every entry's group to 1000, which only matters to other members of that host group. Files the git user creates belong to uid 1500 on the host: a host account that edits workspaces by hand needs to be in gid 1000 (`sudo groupadd -g 1000 <name> && sudo usermod -aG <name> <user>`, then log in again) or use sudo.
- **The drop** (`workspace_user_argv`): every process RoboCo starts in a workspace (git, the file read/write helpers, the hook lookup, `archive_workspace_ref`, the conventions validator, the relay's `upload-pack`) runs as `[/usr/local/libexec/roboco/as-git-user, --timeout, <secs>, --grace, 10, --, *argv]`. The helper (`docker/as-git-user/as-git-user.c`, static, compiled in the image's builder stage) is set-user-id and set-group-id to the git user, owner `1500:1000`, mode `6750`, never set-id root, with both ids compiled in (0 fails the build). It refuses (exit 126, an `as-git-user:` line on stderr) unless its set-id bits took effect (they don't under `no_new_privs` or on a nosuid mount), clears groups for a root caller and refuses any other caller holding a group besides 1000 (a non-root process cannot drop one, so a `group_add` on the service fails loudly), then `setresgid`/`setresuid`, `no_new_privs`, every capability set emptied. As a set-id program it runs in glibc's secure mode, which drops `LD_*`, `GCONV_PATH`, `TMPDIR` and the like: `workspace_git_env` sets none, and an in-image test pins that the environment reaches the program unchanged. **The helper owns the deadline** (there is no `timeout` in the chain, so the caller never needs to signal a git-user process): it makes itself a child subreaper (`PR_SET_CHILD_SUBREAPER`), forks the command into a new session (its own process group) with the environment and signal mask it got, forwards INT/QUIT/HUP/TERM to that group, and waits for the command and for anything the command left running. At the deadline it sends TERM to the group and to its own children; after the grace it SIGKILLs the group and each of its children, again after every death, until none is left. As subreaper it inherits the children of every process of the tree that dies, so a grandchild that ignores TERM and a process that left the group with `setsid` are killed too, within deadline + grace. It signals only the command's group (its id stays allocated because the command is reaped last) and its own not-yet-reaped children, never `kill(-1)`, which as uid 1500 would also kill other workspace commands running at the same time. Exit 124 when the deadline came while the command ran; otherwise the command's exit status, or its terminating signal raised on the helper (no core dump of its own); a command that finished in time keeps its status even when something it left running is killed at the deadline. A failed exec is the command's own 127/126 (`failed to run command '<program>': ...`); only a refusal is 126 with an `as-git-user:` line. Callers wait `workspace_user_wait_seconds` (secs + 10 s grace + 5 s), tolerate `PermissionError` when they kill, and raise an exit 124 past the deadline as `TimeoutExpired`. The command runs as the same uid as the helper, so a command that kills its own helper leaves its tree unbounded; nothing RoboCo runs does that. The kernel ignores set-id bits under `no_new_privs`, so the orchestrator services must never get `security_opt: no-new-privileges`; throwaway containers set it, so the helper refuses there (they unset `ROBOCO_WORKSPACE_GIT_DROP` before a project's code runs).
- **Fail closed** (`settings.workspace_git_drop`, `ROBOCO_WORKSPACE_GIT_DROP`): `required` in the orchestrator image (its Dockerfile sets it), `off` by default (dev and CI on the host, where processes run as the caller). Required: a missing helper or a helper refusal raises `GitUserDropError` and nothing runs as the orchestrator instead; the api and dispatcher (and `all`) refuse to start (`bootstrap.main`, before the database) unless `cat /proc/self/status` started through the helper shows uid 1500 x4, gid 1000 x4, no group but 1000, `NoNewPrivs: 1` and no capability (`verify_git_user_drop`); and the permission repair, `prepare_clone_parent` and `remove_workspace_tree` take their descriptor-based paths. Those used to be chosen by `euid == 0`, which as non-root silently skipped the drop; now only the setting chooses.
- **The orchestrator's own git** in `/data/private` (`git_relay._private_env`) reads `/opt/roboco/git/private.gitconfig` (`safe.directory = *`, root-owned) as its global config: both deploy colors share those repositories and need not run as the same uid. The image itself still sets no global `safe.directory`.
- `tests/unit/services/test_git_runs_only_through_the_runners.py` fails if any other module starts git (including through `run_as_workspace_user` / `workspace_user_argv`), builds a `["git", ...]` argv to start later, or builds git credentials; `tests/integration/test_hostile_workspace_clone.py` is the hostile-clone suite. `scripts/orchestrator_image_suites.sh IMAGE WORKDIR` runs it, `tests/integration/test_git_user_helper_live.py` and the live workspace-container and Entire hook suites inside a built image as root, failing on any skip; the "Orchestrator image suites" workflow runs the same script.
- **Docker** is reached only through the `docker` CLI, and `roboco/utils/docker_subcommands.py` lists every subcommand RoboCo runs. `tests/unit/utils/test_docker_runs_only_listed_subcommands.py` reads every docker argv in `roboco/` (a `["docker", ...]` list wherever it is built, which covers the spawn argv every agent provider extends; `create_subprocess_exec("docker", ...)`; the sandbox runner's callers) and fails on a subcommand the list lacks, on a listed one nothing runs, and on an argv whose subcommand it cannot read, so adding a docker call means adding its subcommand to the list. An inspect always names its object type (`docker container inspect`, `docker image inspect`): a bare `docker inspect` of a name no container has goes on to report an image, network or volume of that name.

**HTTPS URLs require tokens** - attempting to clone without a token will raise `WorkspaceError`.

### Forge providers (GitHub + Gitea + GitLab)

The REST surface (PRs, CI status, reviews, labels, releases) is provider-routed (`roboco/services/forge/`): `GitProvider` is the ~20-method transport contract, `GitHubProvider`, `GiteaProvider`, and `GitLabProvider` implement it, and `GitService._forge` returns a `ForgeRouter` that picks the transport per call from `RepoRef.host` - `None` (github.com/GHE) rides GitHub, a registered Gitea/GitLab host rides that instance's provider, so `GitService`'s call sites never know which forge they're on. A project opts in via `projects.git_provider` (gitlab.com auto-detects like github.com; self-hosted instances set it explicitly; `"github"` doubles as the GHE escape hatch with `ROBOCO_GITHUB_API_BASE_URL`) - panel: the Forge select on the project settings page's identity card (`/projects/[id]/settings`, Wave C - was the edit-project dialog, now deleted). The host→provider(+scheme - plain-http LAN instances are supported) map is in-memory per process, self-healing: `ProjectService.get`/`get_by_slug` re-register on every read. Both non-GitHub providers adapt their wire contracts back into the GitHub shapes `GitService` classifies (`forge/shaping.py` `ShapedResponse`): Gitea - `token` auth scheme, duplicate-PR 409→422, commit statuses reshaped into `check_runs`/`workflow_runs`, `Do`-keyed POST merge, slash-encoded refs; GitLab - MR iid→`number`, source/target_branch→`head`/`base`, per-file diffs reassembled into unified-diff text, approve-vs-note review routing (no request-changes verb exists), pipelines/statuses CI reshapes, reviewer-request skipped (needs numeric ids). Neither has GitHub's server-side merges API: their `merge_branch` returns a shaped 501 and `GitService.sync_env_branch` runs the shared local-git fallback (`_local_merge_branch`: throwaway clone → merge → push; conflict aborts with the remote untouched, same status vocabulary). The server-side commit calls (`create_branch_ref`, `update_branch_ref`, GraphQL `create_commit_on_branch`) exist so GitHub writes and signs the release manager's commits; Gitea and GitLab answer them with the same shaped 501 (`shaping.not_implemented`), and the release executor then pushes the clone's commits with git. Plain git (clone/fetch/push) is forge-agnostic - the Basic-auth `x-access-token:<token>` extraheader works on Gitea/GitLab unchanged (verified live on Gitea). The env-gated `tests/e2e_smoke/test_gitea_live.py` is the live contract suite (self-seeding against a dockerized `gitea/gitea`; it caught the slash-encoding and http-scheme gaps).

### Protected Branches

`projects.protected_branches` (operator-declared, panel: a chips editor on the project settings page's placement card) is unioned - never replacing, only tightening - into `GitService`'s hardcoded safety floor. Two scopes, deliberately different: `_protected_branches_for` (rebase refusal + `sync_task_branch`'s force-push refusal) is the field alone unioned with the hardcoded `{master, main}` floor and fails OPEN on a lookup error (a wrongly-blocked rebase over a transient DB blip is the worse tradeoff, and a skipped rebase gets no free retry); `_protected_branches_for_deletion` - consulted ONLY by the shared `_delete_remote_branch_best_effort` chokepoint every remote-delete path routes through (task-branch cleanup on cancel, the stale-branch sweep, and post-merge PR-source cleanup) - additionally unions in the project's environment-ladder rung branches (`effective_environments`, so a null ladder's synthesized single rung off `default_branch` is protected too, e.g. a renamed trunk like `trunk`) and fails CLOSED on a lookup error (skip the delete entirely; deletion is best-effort so a skipped one just retries at the next sweep, whereas silently proceeding on an unresolvable project could delete a real declared rung for good). Matching is exact and case-sensitive; an empty `protected_branches` list degrades to exactly the prior hardcoded-only behavior.
